# 播放诊断与 Xbox 验证

## 1.0.7 HDR10 片源与 SDR 色调映射

`BV12Bn86nEXE` 的问题需要分别回答「能否解码真实 4K HDR10 片源」和「能否向显示设备输出 HDR10」。只因后者不可用而把整个真实 4K 轨道排除，会让支持 4K SDR 的设备也没有 4K 选项。微软说明原生媒体管线支持 HDR10 内容在 SDR 显示模式中自动色调映射，参见 [Xbox 4K 显示模式文档](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/hevc-xbox)。

1.0.7 对有效的 4K/10bit HDR10 轨道保留原始编码、分辨率、轨道编号及 PQ/BT2020 清单信息，分别查询真实尺寸的解码能力和 SDR 输出能力。两者通过后，提供实际 4K SDR 播放路径，由系统负责颜色映射；如果同档有正常 SDR 轨道，优先选择正常 SDR。不会通过剥掉 HDR 元数据把它伪装成原生 SDR，也不会把 1080P 放大冒充 4K。

映射后的有效画质为 4K 档位，原始轨道档位仍记录为 `sourceQn`，例如有效 `qn=120` 与原始 `sourceQn=125`。`IsHdr10` 继续表示片源，`sdrToneMapping` 与 `outputRange=SDR-tone-mapped` 表示输出路径；界面显示「视频源：HDR10 → SDR（系统色调映射）」。控制器只请求真实 SDR HDMI 模式，`Hdr10Active` 保持 false。缺少 HDR10 输出能力时 HDR10 输出选项仍隐藏，不能用 4K SDR 模式声称 HDR10 已启用。

实机用同一会员账号打开 `BV12Bn86nEXE`，电视只提供 4K SDR 时检查 4K 行是否可选择，实际源尺寸是否为真实 2160P，以及电视是否进入 UHD SDR。下载日志核对实际解码、独立 SDR 证明、原始档位与映射路径。如果原始轨道不能解码或没有已确认的 SDR 输出，不允许仅靠映射标记绕过检查；画质回退仍使用真实兼容来源。

## 1.0.7 高帧率接口声明的兼容试播

`BV1F4Ex6xEqX` 的截图含 119.994/119.993fps 声明。仅凭该字段既不能确定码流确为此帧率，也不能断定它一定错误。1.0.7 把超过 60fps、约不超过 120fps（含数值容差）的声明作为显式兼容试播候选：保留原始值，以相同编码、真实尺寸、码率和位深查询 60fps 基准，确认对应输出后交给原生解析与试播。超过该上界的来源不沿用这个例外。

60fps 基准查询通过只证明基准能力，不证明 119.99/120fps 硬件解码。实际 HDMI 媒体输出仍为受支持的不超过 60Hz 模式，不请求 120Hz，也不把码流或清单帧率改写为虚假的 60fps。画质行标注「兼容试播」，账号的「需要登录/需要大会员」仍独立约束是否能选择。

原生解析确认实际 4K 尺寸且帧率在 60fps 范围内时，可记为校验通过并取消当前画质行的试播标记；原生仍报告高帧率或元数据尚不明确时，继续显示未确认的兼容试播状态。原生尺寸不符、超过试播上界、打开错误或持续播放失败仍遵循有限回退，不保证该视频在 Xbox 上能持续流畅播放。

实机对 `BV1F4Ex6xEqX` 选择标有「兼容试播」的实际 4K 来源，核对 `reportedFps` 仍保留约 119.99，`probeFps=60`，再查看 `nativeFps`、`nativeFpsVerified` 与原生校验/试播事件。不能把选择成功或电视显示 4K60 等同于已实现 4K120 解码。

## 1.0.6 等待缓存与原生停滞恢复

`BV12kWU63EVt` 的报告显示 4K HEVC 59.94fps、视频码率约 10.94Mbps，某次接收速度为 4.18MB/s，但可播缓存约 1.2 秒且反复归零。速度是短时间采样，不能据此证明全程网络稳定，也不能单凭平均视频码率推断后续下载、音视频同步和解码始终跟得上。

检查生产代码确认一个独立的控制逻辑缺陷：应用在重新缓冲时会主动暂停，等待真实连续缓存达到 3 秒；但另一个原生解码停滞检测从 2 秒缓存起就可能把冻结的播放时钟视为解码停滞。如果应用主动停在 2 至不足 3 秒之间，这个预期中的暂停也可能在 12 秒后触发一次播放源重建，从而丢掉已经积累的缓存。它能解释一种缓存被不必要重置的路径，但没有本次完整运行日志，不能断定视频中的全部卡顿都由此造成。

现在原生停滞恢复明确排除应用自己为等待缓存而主动暂停的阶段，保留同一媒体源继续积累数据；实际达到 3 秒后仍只请求一次恢复。恢复前不再无条件额外暂停一次，避免打断首次原生缓冲，或重复暂停已经由应用停下的媒体源。恢复请求已经交还原生播放器、但原生仍有充足缓存且时钟持续不前时，原有解码停滞恢复仍可执行。这个区分不把所有缓冲状态都屏蔽，不提高等待门槛，也不取消真正无数据时的有限备用来源恢复。

实机复测时记录同一次播放的接收速度、连续可播缓存及进度变化。等待阶段已有约 2.5 秒缓存时，不应仅因等待超过 12 秒就重新连接；达到 3 秒后应继续播放，用户主动暂停不能被自动恢复覆盖。若仍卡顿，请对照 `source-open-attempt`、实际原生尺寸/编码和错误记录，确认是否重新打开了媒体源，再区分网络、同步和解码问题。单次速度数字不足以确定其中哪一种原因。

## 1.0.6 DCI 4K 与 UHD 输出尺寸

`BV1kX4y197P4` 的截图显示 HEVC 片源为 3996×2160、25fps、8bit，解码查询返回 `Probably`，显示查询返回 `NotSupported`，而 HDMI 最高模式为 3840×2160。旧代码同时把片源尺寸用于解码与输出查询，还要求 HDMI 模式宽度至少为 3996。这把「能解码 3996 像素宽的片源」与「需要 3996 像素宽的输出模式」混为一谈，导致已有 UHD 输出模式不能参与选择。

现在解码查询保留实际 `decode-res-x=3996,decode-res-y=2160`。对于长边超过 3840 且不超过 4096、短边不超过 2160 的 DCI 宽度片源，独立检查 `display-res-x=3840,display-res-y=2160`，实际播放也选择受支持的 UHD HDMI 模式。原始码流和解码尺寸保持不变，由原生画面显示按比例适配电视表面；这不是将低清视频插值为 4K，也不意味着 DCI 片源每个像素都能与 UHD 面板逐点对应。

此处理不会绕过实际解码拒绝，不把 8K、超过 4096 的宽度或超过 2160 的短边一律改成 UHD。正常 3840×2160、4∶3 2160P 和裁切宽银幕仍保留原有判断。SDR 与 HDR10 分别验证，SDR 输出不能作为 HDR10 的支持证明。

实机复测 `BV1kX4y197P4`，先核对原生片源尺寸是否仍为 3996×2160；日志应分别保留真实解码尺寸和 `source=3996x2160 output=3840x2160`。选择 4K 后电视应进入受支持的 UHD 模式；若解码拒绝、输出设置失败或实际播放失败，仍应记录对应原因并使用已有真实回退源。仅有菜单中的 4K 标签不能证明解码或输出已经成功。

## 1.0.6 Hi-Res 音频

播放设置中的「Hi-Res 无损」使用 B 站实际返回的 `dash.flac.audio`，而不是为标准 AAC 增加音效或改名。应用检查登录、大会员与系统 FLAC 解码器；本次没有返回可用 FLAC、权限不足或系统不能解码时说明具体原因。切换保留视频画质、时间位置和暂停意图，原生音频失败时先尝试同一视频的标准 AAC 音轨，再按已有视频候选链回退。

音频详情只显示接口或原生轨道中实际已知的编码、采样率、位深与声道。缺少数据时保持未知，不默认补成 96kHz/24bit，也不把标准音频或杜比音频当作 FLAC。选中 Hi-Res 证明所选片源为实际 FLAC；Xbox 的混音、重采样、HDMI/功放及系统输出设置仍会影响最终输出，应用不能仅凭所选音轨证明逐位不变的高解析音频输出。

实机使用提供 Hi-Res 的同一视频和会员账号，在「标准音频 → Hi-Res 无损 → 杜比音效」间切换，核对实际编码、显示参数、位置与暂停状态。未登录、非会员、片源缺失和解码器不可用分别验证提示；音轨失败时确认仍可播放同画质视频，且界面如实显示回退后的音频。测试不需要发布评论、弹幕或其他账号写入操作。

## 接口帧率与实际时间戳调查

本轮对 `BV1AM4y1M71p`（截图中的《新宝岛》）进行了公开匿名读取。480P HEVC 的接口帧率为 30.303，AVC 为 29.412；同条响应的 `frameRate` 与 `frame_rate` 一致，没有发现应用把 30fps 算成 62.5fps 的转换。对两条媒体源各最多读取 1MiB、各检查 60 个视频包的时间戳，得到约 1.9993125 秒和 2.0003125 秒的区间，对应约 30.0103fps 和 29.9953fps；FFmpeg 解析为 30fps。这组证据表明该响应的帧率字段不能直接等同于实际帧间时间戳。

取样只覆盖各自很短的 480P 片段，不代表整条视频恒定帧率，也不能用它证明需要会员的 4K 轨道实际帧率。62.5 恰好等于 16 毫秒的倒数，但 B 站内部如何生成该字段尚未证实，不能把这个数值关系当成已查明的根因。

另一个报告视频 `BV1F4Ex6xEqX` 的截图分别显示 4K HEVC HDR 为 119.994fps、SDR 为 119.993fps。本机匿名返回的 480P 约 30fps，不能据此判定会员 4K 也只有 30fps，或断言 119.99fps 必然是错误元数据。需要同一账号的实际 4K 轨道属性及时间戳才能进一步确认；本轮未取得该会员轨道的码流验证结果。

微软文档列出的 `decode-fps` 查询参数最高为 60，并说明 Xbox UWP 媒体播放不支持 120Hz 输出模式。前者说明该查询不能直接表达 119.99/120fps，后者是媒体输出模式限制；它们不是一次针对该 4K 轨道的硬件解码拒绝结果。应用保持这些边界，不把 119.99/120fps 钳制成已验证的 60fps，也不承诺实现 120fps 播放。参考微软[查询参数](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/supported-play-type-strings)及 [Xbox 媒体输出模式](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/hevc-xbox)。

## 1.0.5 接口声明 62.5fps 的 4K 轨道

`BV1ct4y1n7t9` 的 Xbox 截图已经显示服务端返回了 `hvc1`、3840×2160、8bit 的轨道，但帧率字段为 62.5fps。旧版显示「媒体能力查询帧率上限为 60fps」和 `query=not-issued`，说明轨道在本地参数校验时就被排除了，并非微软 API 已明确拒绝此轨道，也不是服务端没有返回 4K。

微软媒体能力查询的 `decode-fps` 只接受文档列举的档位，最高为 60。1.0.5 保留接口原始声明；对于超过 60fps、但不超过 63fps 的接近 60fps 声明，使用 60fps 档位检查相同编码、真实尺寸、位深和输出要求的基础能力。只有基础查询通过，才允许原生解析与 60Hz 试播。这不等于确认 62.5fps 的硬件支持，也不适用于任意高帧率，例如 120fps。参见微软[支持的查询字符串](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/supported-play-type-strings)。

特殊路径将媒体源包装为 `MediaPlaybackItem`，在 `MediaOpened` 后读取所选视频轨道的原生编码属性。原生解析帧率在 60fps 范围内且实际 4K 尺寸已确认时，记录校验通过；帧率仍为 62.5 或尚不明确时，明确显示试播状态。若原生尺寸与 4K 声明不符或帧率超过试播范围，尝试下一条真实视频轨道，随后保留原有画质回退。原生打开错误、播放失败与停滞恢复机制继续生效。

此路径不会把接口的 62.5 改成真实 60fps，不重采样视频，也不把 1080P 放大或插值冒充 4K。DASH 清单不写入不可信的超 60fps 提示，也不替换为伪造的 60fps；实际码流交由原生解析器读取。

日志中的 `reportedFps`、`probeFps`、`nativeFps` 分别表示接口声明、能力查询参数和原生解析值；`nativeTrial` 与 `nativeFpsVerified` 表示是否使用特殊路径及是否完成原生校验。对应事件为 `native-frame-rate-verified`、`native-frame-rate-trial` 或 `native-frame-rate-rejected`，附加内容保留 `api-fps`、`query-fps`、`native-fps` 与原生宽高。没有原生解析值时会记录为 0，不能把它理解成实际视频为 0fps。

实机使用相同会员账号打开 `BV1ct4y1n7t9`，确认 4K 选项不再仅因接口的 62.5fps 声明消失。选择后检查日志应发出 `decode-fps=60` 的能力查询，原始声明仍为 62.5；再核对原生 3840×2160、校验/试播事件和持续播放表现。若仍回退，请保留该次完整逐轨日志，区分基础能力拒绝、原生尺寸/帧率不适用、HDMI 设置失败与实际播放失败。此修复尚不能仅凭本机测试保证该视频在 Xbox 上持续流畅播放。

## 1.0.4 多轨道筛选

同一清晰度可能包含多条视频轨道。每条都独立检查编码、真实尺寸、位深、帧率与输出要求，优先选择兼容的 HEVC。同一档位某条 HDR 轨道失败，不能阻止 SDR 轨道或其他已确认编码的协商。只有完成逐轨检查后才汇总清晰度状态。

`ProtectionCapabilityResult.Probably` 的枚举值为 2，表示查询当时支持；它应按支持处理，不能按布尔值或 `==1` 判断。`Maybe` 保持未确认状态，`NotSupported` 才是系统明确不支持。SDR 的解码位深可以为 10bit，但输出仍查询 8bit SDR；HDR10 则分别验证 10bit 解码与 10bit/PQ 输出。参见微软[枚举定义](https://learn.microsoft.com/en-us/uwp/api/windows.media.protection.protectioncapabilityresult)。

某条轨道通过能力检测但原生打开、输出准备或实际播放仍失败时，先逐条尝试同档其他兼容来源，最后才退到较低画质。候选链按实际来源去重、有次数限制且不能成环；杜比优先回退同一视频轨道的 AAC 音频。

日志通过原始数组下标定位轨道，同时记录编码、SDR/HDR10、位深、帧率和完整查询结果。候选记录不代表已播放；应对照 `selected`、`source-open-attempt` 与 `media-opened` 的轨道下标及 `native` 尺寸。预过滤的版权/无效分段轨道也要有具体拒绝原因。长报告按 `report`/`part` 分块写入；异常超大报告或队列超限会留下明确提示，不静默丢失末尾。

实机验证可使用同一会员账号与 BV（本轮报告为 `BV1ct4y1n7t9`），按 1080P→4K 操作后下载日志，核对所有 `qn=120` 轨道是否检查过，以及 API 选择与原生打开的编码是否一致。公开读取受到 HTTP 412 限制时，不能用匿名结果推断登录 Xbox 的真实返回。

## 1.0.3 音频与缓冲验证

在播放设置的「音频」中选择杜比。应用读取 `dash.dolby.audio` 的真实 `ec-3/ac-3` 音轨，检查当前登录会员与系统 `CodecQuery` 解码器；日志记录请求模式、实际编码、声道（仅在已知时）、可用原因。不会把普通 AAC 或声道数量推断为 Dolby Atmos。输出是否为杜比比特流取决于 Xbox 音频设置、电视/功放与连接方式，不能仅凭选中音轨断定已直通。

验证：会员使用提供杜比音频的同一个视频，切换标准/杜比时确认画质、时间位置与暂停状态保持。非会员和未登录账号分别看到权限提示；缺音轨或设备不支持时保留标准音频。系统播放器失败时优先回退同画质 AAC，不反复重开同一失败来源。参考微软 [CodecQuery 文档](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/codec-query)。

缓冲使用 `MediaPlaybackSession.GetBufferedRanges()` 的真实连续可播范围。DASH `minBufferTime` 为 3 秒；初次缓冲已有 3 秒时尝试恢复，真正重缓冲后保持播放意图并等待 3 秒，再尝试一次恢复。第一次下载尚未启动时不会先暂停；未知范围交回原生处理，片尾剩余不足 3 秒允许结束。定位、换音轨、关闭播放器、打开其他页面和用户暂停会使旧恢复任务失效。原生解码、关键帧和同步可能继续等待，不能用网络字节数假称已可播放。

实机可在较慢网络下观察「可播缓存」，核对首次及再次缓冲时约 3 秒恢复、暂停期间不自行播放、片尾不等待凑满 3 秒。播放器 LB/RB 分别后退/前进 5 秒，暂停时应保持暂停；首页切分区和图片换图各自保持原行为。

## 1.0.2 修复的原因

旧的筛选同时要求超高清轨道长边至少为 3840，会排除 2880×2160 等 4∶3 的 2160P 轨道。菜单还主要依赖 `accept_quality`；如果实际 DASH 返回了 4K 轨道，却未将它列入该字段，菜单可能漏项。另一个限制是 AV1 在解析入口被统一排除。

现在结合真实轨道编号、尺寸、编码、分段、解码能力和显示能力判断。2160P 的 4∶3、竖屏以及长边达到 3840 的裁切宽银幕可以参与筛选。菜单补入实际返回的可用轨道，始终显示实际尺寸；不会把 1920×1080 的流重命名为 4K，也没有插值生成 4K 的过程。

这些是代码中已确认的缺陷。单个视频在特定账号、地区和设备上是否返回 4K，仍以当次响应为准；公开接口受到 HTTP 412 限制时，无法据此推断登录账号的实际播放权限。

## 请求与编码

- 普通投稿读取签名的 `/x/player/wbi/playurl`，传递所选 `qn`，4K 为 `qn=120`，并带 `fnval=2000`、`fnver=0`、`fourk=1`。默认 1080P 请求不会被虚构成 4K 请求，选择 4K 后会单独获取对应档位。
- `fnval=2000` 优先协商 AVC/HEVC。明确请求超高清但没有可用轨道时，只有微软硬件能力查询确认支持 AV1，才最多追加一次 `fnval=4048` 协商；失败保留原来源，不循环请求。
- H.264、HEVC 和 AV1 分别识别；AV1 用实际位深、分辨率、帧率和码率查询支持。Xbox H.264 的限制依照微软公布的 1080P60 范围，不能用桌面可播放等同于 Xbox 可播放。
- 已登录请求通过现有 Cookie 存储发送 `SESSDATA`；响应检查会话是否改变，防止切换账号后继续使用旧响应。日志只记录会话存在、登录、大会员等布尔状态，不写凭证值。
- 可用 HDMI 模式来自 `GetSupportedDisplayModes()`。实际播放前申请适合片源的输出模式，再核对当前模式；首页当前为 1080P 不会单独决定 4K 选项是否出现。

微软参考：[Xbox 4K 播放](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/hevc-xbox)、[媒体能力查询字符串](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/supported-play-type-strings)、[Xbox 支持的技术](https://learn.microsoft.com/en-us/windows/uwp/apps-for-xbox/supported-technologies)。

## 诊断分类

| 分类 | 含义与处理 |
| --- | --- |
| `ServerNotReturned` | 服务端没有实际返回所请求档位的轨道；保留真实较低画质，不宣称设备一定不支持。 |
| `DeviceUnsupported` | 有轨道，但硬件解码或显示能力拒绝；隐藏不支持的选项并保留原因。 |
| `CapabilityUnconfirmed` | 能力查询无法确认；保留待确认状态，避免把查询失败当成确定支持。 |
| `SourceUnsupported` | 编码/分段/HDR 格式不兼容，或所谓超高清轨道实际尺寸不足。 |
| `DisplayFailed` | 能力查询通过，但实际 HDMI 模式设置失败；使用已授权的兼容回退源。 |
| `PlaybackFailed` | 原生播放器实际打开或播放失败；记录错误类型、HRESULT，有兼容源时自动回退。 |

回退来源取自同一视频的真实授权响应，不自动提高权限，不用低清流冒充所选档位。菜单和“当前画质”表示的是不同状态：可选择 4K 并不代表已经成功播放 4K。

## 日志位置

在 Xbox Device Portal 的应用文件浏览器中选择已安装的弹幕舱，打开其 `LocalState`，下载：

- `playback-diagnostics.log`
- `playback-diagnostics.previous.log`（发生轮转后才存在）

日志在后台写入，并限制单条、队列和文件大小。包括请求参数、画质列表、权限标记、每条轨道的尺寸/编码/帧率/码率/位深、被排除原因、微软能力查询，以及原生播放器实际打开后的 `native=宽x高`。特殊帧率路径还记录接口、查询与原生帧率及校验/试播状态。不保存完整 API JSON、媒体地址、Cookie、密码或账号 ID。请等播放设置更新完成后再下载日志，按时间对照操作。

## Xbox 实机验证

1. 安装本次签名测试包，登录与手机相同的大会员账号。选用同一个 BV 和分 P，例如报告问题时使用的 `BV1d4411N7zD`。
2. Xbox 首页输出设置为 1080P，保持“允许 4K”开启，先以 1080P 播放，再打开画质设置选择 4K。记录选项是否出现、当前实际尺寸及是否成功切换 HDMI。
3. 对照日志：`qn=120`、`fourk=1`、`auth=True`、`sessionCookie=True`；查看有没有 `track qn=120`，其真实尺寸、编码和 `decision`。缺档与编码被排除应得到不同分类。
4. 4∶3 2160P 应保留其 2880×2160 等实际尺寸；常规 UHD 通常为 3840×2160。对照 `media-opened native=...` 与电视的信息面板，不能仅凭菜单名称或电视处于 4K 输出断定片源是 4K。
5. 验证自动回退：发生不支持的编码、输出模式失败或原生播放器错误后，应播放明确标注的真实兼容画质，不能一直重试同一高画质。
6. 同时回归暂停/恢复、切分 P、弹幕、评论和楼中楼。观看后打开历史；切换推荐/热门再返回应保留卡片与位置，只有主动刷新才换批。切换账号后不得出现上一账号历史。

纯代码测试和本机原生构建不能代替 Xbox 的 HDMI、解码和持续播放测试。若手机有 4K 而 Xbox 仍缺失，以上日志能够区分服务端差异、账号状态、轨道格式与设备拒绝，避免仅凭现象猜测。
